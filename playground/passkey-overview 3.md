## Introduction

Passkeys represent a modern authentication approach based on the FIDO2/WebAuthn standard, designed to replace traditional passwords with public-key cryptography. This paper summarizes the key technical and practical aspects of passkeys based on current implementation patterns.

## 1. Passkey Providers

Passkeys are generated and managed by **passkey providers** that operate at the platform level:

- **Apple** (iCloud Keychain) - syncs across iOS, iPadOS, and macOS
- **Google** (Google Password Manager) - syncs across Android, Chrome OS, and Chrome browser
- **Microsoft** (Windows Hello) - primarily Windows-based, with some cross-platform support
- **Third-party password managers** - 1Password, Bitwarden, Dashlane (emerging support)
- **Hardware security keys** - YubiKey, Google Titan (device-bound, no sync)

The provider ecosystem is currently fragmented, with each operating primarily within its own platform boundaries.

## 2. Local Architecture: Biometrics and Key Pairs

The passkey architecture maintains a critical separation between authentication and cryptographic operations:

**Key generation (registration):**
- Provider generates a public/private key pair specific to the application and user
- Public key is sent to the service (e.g., GitHub)
- Private key remains on the device (or in encrypted keychain storage)

**Authentication (login):**
- Service sends a cryptographic challenge
- User authenticates **locally** with biometrics (Face ID, Touch ID, fingerprint, etc.)
- **Biometrics never leave the device** - they only authorize use of the private key
- Device signs the challenge with the private key
- Service verifies the signature using the stored public key

This design ensures biometric data remains private and local, never transmitted to or stored by applications.

## 3. Cross-Device Synchronization

Passkey providers enable convenience through encrypted synchronization:

**Synced passkeys:**
- Private keys are encrypted and synced via the provider's cloud infrastructure (iCloud, Google servers, etc.)
- All devices in the same ecosystem can access the same passkey
- Example: One passkey for GitHub works across your iPhone, iPad, and Mac

**Device-bound passkeys:**
- Hardware security keys store keys locally without sync
- Each device requires its own separate passkey registration
- Higher security at the cost of convenience

The sync mechanism means that when you create a passkey on one device, it becomes available on all devices within that provider's ecosystem after secure synchronization.

## 4. Browser and Platform Dependencies

A critical architectural constraint: **browsers must tap into the platform's passkey service**.

**How it works:**
- Browsers don't implement passkey support independently
- They query the operating system's passkey provider through standard APIs
- Safari on macOS uses iCloud Keychain
- Chrome on Windows uses Windows Hello
- Chrome can access iCloud Keychain on macOS through Apple's extension

**The restriction:**
- Your available passkeys depend on which platform you're on, not which browser you use
- Opera on macOS can access iCloud Keychain passkeys
- Opera on Windows cannot access iCloud Keychain (different ecosystem)
- Cross-platform work requires either multi-platform providers (like 1Password) or multiple registrations

This creates friction for users who work across multiple operating systems.

## 5. One Passkey Per Application

The FIDO2/WebAuthn standard enforces **domain-specific passkeys** - each application gets its own unique key pair. This is analogous to best practices for passwords (one password per site), but enforced at the protocol level.

**Why not a single universal passkey?**

**Domain binding (anti-phishing):**
- Each passkey is cryptographically bound to a specific domain (github.com, twitter.com, etc.)
- The domain is included in the cryptographic signature
- Phishing sites cannot trick your device into using a passkey meant for another domain
- This protection works automatically without user awareness

**Privacy protection:**
- Unique public keys per site prevent cross-site tracking
- Services cannot correlate your identity across platforms using your public key

**Security isolation:**
- Compromise of one service doesn't affect other accounts
- Each passkey failure is isolated to that specific application

The architecture deliberately prevents passkey reuse to build security and privacy into the foundation.

## 6. Advantages

**Security improvements:**
- **Phishing-resistant** - domain binding prevents credential theft through fake sites
- **No password reuse** - each site gets unique credentials automatically
- **No password leaks** - nothing secret to leak in a database breach (only public keys stored)
- **Resistant to credential stuffing** - stolen credentials from one site can't be used elsewhere

**User experience:**
- **Simpler login** - biometric authentication is faster than typing passwords
- **No password reset flow** - can't forget your passkey
- **Cross-device convenience** - synced passkeys work across all your devices

**Technical benefits:**
- **Standards-based** - FIDO2/WebAuthn are open standards with broad industry support
- **Cryptographically sound** - based on well-established public-key cryptography
- **Future-proof** - designed to evolve with new authentication methods

## 7. Shortcomings and Weak Points

**Ecosystem lock-in:**
- Passkeys are typically bound to provider ecosystems (Apple, Google, Microsoft)
- Moving between ecosystems requires re-registering all passkeys
- No easy export/import mechanism across providers

**Cross-platform friction:**
- Users working on multiple platforms (Mac + Windows, iPhone + Android) face challenges
- Must either use cross-platform password managers or maintain multiple passkey registrations
- The promise of convenience breaks down outside a single ecosystem

**Account recovery complexity:**
- If you lose access to all devices with your passkeys, recovery can be difficult
- Services must still maintain fallback authentication methods
- Recovery mechanisms can reintroduce vulnerabilities passkeys were meant to eliminate

**User understanding:**
- Conceptually more complex than passwords
- Users may not understand where their passkeys are stored or how sync works
- Troubleshooting authentication failures requires understanding the provider layer

**Limited adoption (see next section):**
- Chicken-and-egg problem: users don't understand passkeys, services slow to adopt
- Legacy systems and services may never support passkeys

**Device dependency:**
- Your authentication capability depends on having a device with your passkeys
- Hardware failure or loss can be more disruptive than forgetting a password
- Requires maintaining backup authentication methods

## 8. Current Availability and Adoption

As of late 2024/early 2025, passkey adoption remains limited:

**Services with passkey support:**
- **Major tech platforms**: Google, Apple, Microsoft accounts
- **Social/communication**: WhatsApp, LinkedIn, TikTok
- **Financial**: PayPal, some banking apps (implementation varies by region)
- **Development**: GitHub, some cloud providers
- **E-commerce**: eBay, Best Buy, select others

**Notably absent or limited:**
- Many banking and financial institutions
- Most e-commerce sites
- Enterprise/corporate systems (often move slowly)
- Smaller services and startups (resource constraints)
- Password managers themselves (ironic, but improving)

**The reality:**
- Passwords will coexist with passkeys for years
- Most users still need a password manager anyway
- Services often implement passkeys as an option, not a replacement
- Cross-service inconsistency in implementation quality

**Rate of adoption:**
- Growing but gradual
- Major services lead, smaller ones lag significantly
- Mobile apps often ahead of web implementations
- Consumer services ahead of enterprise/B2B

## Conclusion

Passkeys represent a significant architectural improvement over passwords, addressing fundamental security weaknesses through cryptographic design. The protocol itself is sound and the security benefits are real - particularly phishing resistance and elimination of password reuse.

However, practical adoption faces challenges: ecosystem fragmentation limits cross-platform usability, user understanding remains low, and service adoption is gradual. The vision of a password-free future is compelling, but the current reality requires users to navigate multiple authentication methods across different services and platforms.

For now, passkeys work best as a complement to, rather than replacement for, traditional password managers. Users within a single ecosystem (all-Apple, all-Google) gain the most benefit with the least friction. Those working across platforms must carefully consider whether passkeys reduce or increase authentication complexity in their specific usage patterns.

The technology is ready; widespread practical deployment remains a work in progress.
